# Пояснительная записка

**Тема:** разработка клиент-серверной системы вычисления арифметических выражений

**Репозиторий:** https://github.com/matvejchukhanov-ops/MIREA

---

## Аннотация

Разработана клиент-серверная система, в которой сервер принимает по протоколу
TCP арифметические выражения, разбирает их собственным синтаксическим
анализатором и возвращает результат клиенту. Транспортный уровень, прикладной
протокол и разбор выражений реализованы самостоятельно, без использования
веб-фреймворков и без функции `eval()`.

Объём: 1908 строк кода в 20 модулях, 957 строк тестов, 129 автоматических
тестов. Внешних зависимостей нет — система работает на стандартной библиотеке
Python.

## 1. Введение

### 1.1 Постановка задачи

Требуется разработать программную систему, построенную по архитектуре
«клиент — сервер», в которой обе стороны взаимодействуют через сеть по
самостоятельно спроектированному протоколу.

В качестве прикладной задачи выбрано вычисление арифметических выражений:
клиент отправляет выражение в текстовом виде, сервер возвращает результат
или сообщение об ошибке.

### 1.2 Цель

Реализовать работоспособную клиент-серверную систему, в которой сетевое
взаимодействие построено на сокетах напрямую, без промежуточных фреймворков,
скрывающих механику передачи данных.

### 1.3 Задачи

1. Спроектировать прикладной протокол поверх TCP и зафиксировать его до
   написания кода.
2. Реализовать сервер, принимающий подключения и обслуживающий нескольких
   клиентов одновременно.
3. Реализовать разбор и вычисление арифметических выражений собственными
   средствами.
4. Обеспечить устойчивость сервера к некорректным и злонамеренным данным.
5. Реализовать клиентское приложение.
6. Покрыть систему автоматическими тестами.

### 1.4 Обоснование выбора прикладной задачи

Вычисление выражений выбрано потому, что оно не требует базы данных и внешних
сервисов, но при этом содержит содержательную вычислительную часть —
синтаксический анализ. Это позволяет сосредоточиться на сетевой стороне
задания, не превращая работу в написание форм и SQL-запросов.

## 2. Анализ предметной области

### 2.1 Клиент-серверная архитектура

Клиент-серверная архитектура распределяет систему между двумя ролями:

- **сервер** — пассивная сторона, которая занимает известный сетевой адрес,
  ожидает обращений и обслуживает их;
- **клиент** — активная сторона, инициирующая соединение.

Важно различать **логическую роль** и **уровень реализации**. Программа может
логически быть сервером (обслуживать множество пользователей, хранить
состояние), но при этом не реализовывать сетевой уровень самостоятельно,
получая его от библиотеки. В настоящей работе сетевой уровень реализуется явно.

### 2.2 Выбор транспортного протокола

| Критерий | TCP | UDP |
|---|---|---|
| Гарантия доставки | есть | нет |
| Сохранение порядка | есть | нет |
| Установление соединения | требуется | не требуется |
| Границы сообщений | **не сохраняются** | сохраняются |
| Накладные расходы | выше | ниже |

Для калькулятора потеря запроса или ответа недопустима, а порядок обмена
существенен. Поэтому выбран TCP. Плата за это — необходимость самостоятельно
восстанавливать границы сообщений.

### 2.3 Проблема границ сообщений

TCP предоставляет приложению **поток байт**, а не последовательность
сообщений. Он гарантирует, что данные дойдут все, в правильном порядке и без
искажений, но не сохраняет соответствие между вызовами передачи и приёма.

Практическое следствие: два вызова передачи на стороне клиента могут прийти
одним чтением на стороне сервера, а одно сообщение — оказаться разрезанным
на произвольные части.

```
Клиент отправил двумя вызовами:   "AAA"    "BBB"

Сервер может получить:
    "AAABBB"           склеилось
    "AAA"  →  "BBB"    совпало
    "AA"  →  "ABB"  →  "B"    разрезало
```

Это свойство было воспроизведено экспериментально на первом этапе разработки
(см. раздел 5.4).

Известны два способа восстановления границ:

| Способ | Достоинства | Недостатки |
|---|---|---|
| Разделитель (перевод строки) | Читаемость, возможность отладки вручную | Требует экранирования разделителя в данных |
| Префикс длины (4 байта) | Работает с любыми данными, включая бинарные | Протокол нечитаем, отладка сложнее |

В работе выбран разделитель: данные текстовые, разделитель в них невозможен
(JSON экранирует переводы строк самостоятельно), а протокол можно набирать
вручную telnet-подобным клиентом.

### 2.4 Способы вычисления выражений

Рассмотрены три подхода.

**Функция `eval()`.** Строка передаётся интерпретатору Python, который
вычисляет её сам. Реализуется одной строкой кода.

Подход отвергнут по соображениям безопасности. `eval()` выполняет произвольный
код Python, а не только арифметику. Строка приходит из сети от произвольного
отправителя; вместо выражения `2 + 2` может быть прислана конструкция,
читающая файлы, запускающая процессы или открывающая доступ к машине. Это
уязвимость класса «удалённое выполнение кода» — одна из наиболее тяжёлых.

Общий принцип, который отсюда следует: **данные, полученные из сети, не
являются кодом и не должны им становиться.**

**Разбор через модуль `ast` с белым списком узлов.** Стандартная библиотека
строит синтаксическое дерево, не выполняя его; программа обходит дерево,
разрешая только арифметические узлы. Подход безопасен, но синтаксический
анализ выполняет интерпретатор, а не разработчик.

**Собственный анализатор.** Реализуется лексический анализатор, синтаксический
анализатор и вычислитель. Выбран этот вариант: он составляет содержательную
часть работы и допускает произвольное расширение языка выражений.

Из известных алгоритмов синтаксического анализа выбран **рекурсивный спуск**
как наиболее прозрачный: каждому правилу грамматики соответствует одна функция,
а приоритет операций возникает из структуры грамматики, а не задаётся таблицей.
Альтернатива — алгоритм сортировочной станции Дейкстры — сравнима по
трудоёмкости, но менее наглядно отражает структуру языка.

## 3. Проектирование

### 3.1 Общая архитектура

Система состоит из трёх частей:

- **`server/`** — серверное приложение;
- **`client/`** — клиентское приложение;
- **`common/`** — код, общий для обеих сторон.

Наличие общей части не случайно: проблема границ сообщений симметрична —
ответ сервера может прийти по частям точно так же, как запрос клиента.
Дублирование этого кода означало бы необходимость исправлять каждую ошибку
дважды.

Диаграмма компонентов приведена в [diagrams.md](diagrams.md), раздел 1.

### 3.2 Слоистая структура сервера

Зависимости направлены строго сверху вниз, нижние слои не знают о верхних:

```
main.py           запуск, разбор аргументов
   ↓
tcp_server.py     слушающий сокет, цикл accept, управление потоками
   ↓
connection.py     обмен с одним клиентом, восстановление кадров
   ↓
protocol.py       разбор запросов, сборка ответов, коды ошибок
   ↓
dispatcher.py     сопоставление имени команды с обработчиком
   ↓
handlers.py       реализация команд
   ↓
calc/             вычислительное ядро
```

Ключевое проектное решение: **пакет `calc/` не зависит от сети.** Снаружи это
функция «строка → число». Благодаря этому вычислительная часть тестируется
без запуска сервера, а отладка синтаксического анализатора не смешивается
с отладкой сетевого взаимодействия.

### 3.3 Прикладной протокол

Протокол зафиксирован в отдельном документе [protocol.md](protocol.md) до
начала написания кода. Без такой фиксации клиент и сервер неизбежно расходятся
в частностях.

Основные решения:

| Аспект | Решение |
|---|---|
| Границы сообщений | одно сообщение — одна строка, завершённая переводом строки |
| Предельный размер кадра | 4096 байт |
| Формат тела | объект JSON в кодировке UTF-8 |
| Модель обмена | «запрос — ответ», сервер не инициирует передачу |
| Признак результата | поле `status` со значением `ok` или `error` |
| Ошибки | машиночитаемый `code` отдельно от текста `message` |

Разделение кода и текста ошибки принципиально: программа принимает решения по
коду, человек читает текст. Разбор текстового сообщения на стороне клиента
привёл бы к поломке при первом же изменении формулировки.

Реализованы четыре команды: `calc`, `ping`, `history`, `quit`. В протоколе
дополнительно заложены расширения (версионирование, аутентификация,
асинхронный режим с сопоставлением по полю `id`), не реализованные в текущей
версии.

### 3.4 Модель конкурентности

Системные вызовы приёма подключения и чтения из сокета являются блокирующими.
Следовательно, однопоточный сервер, начав обслуживание клиента, не вернётся
к приёму новых подключений до его отключения.

Рассмотрены варианты:

| Модель | Простота | Масштабируемость | Выбор |
|---|---|---|---|
| Последовательная | максимальная | один клиент | использована на этапах 1–6 как демонстрация проблемы |
| Поток на клиента | высокая | сотни клиентов | **выбрана** |
| Пул потоков | средняя | сотни клиентов | избыточно при известном пределе |
| Асинхронный ввод-вывод | низкая | десятки тысяч | избыточно для учебной задачи |

Выбрана модель «поток на клиента». Главный поток выполняет только приём
подключений, обмен ведётся в отдельных потоках.

Существенное проектное следствие: **разделяемое изменяемое состояние сведено
к минимуму.** Буфер чтения и история вычислений принадлежат конкретному
соединению и живут внутри своего потока. Единственная общая величина — счётчик
активных подключений, защищённый блокировкой, поскольку операция «прочитать,
увеличить, записать» не является атомарной.

Такой подход надёжнее расстановки блокировок: он устраняет условия
возникновения состязаний, а не борется с их последствиями.

### 3.5 Грамматика выражений

```
выражение  :=  слагаемое  ( ( "+" | "-" )  слагаемое )*
слагаемое  :=  множитель ( ( "*" | "/" )  множитель )*
множитель  :=  ЧИСЛО
            |  "(" выражение ")"
            |  ( "-" | "+" ) множитель
```

Приоритет операций **не задан явно** — ни таблицей, ни числовыми весами. Он
следует из структуры: правило «выражение» состоит из «слагаемых», а
«слагаемое» — из «множителей», поэтому умножение располагается глубже в дереве
разбора, а вычисление идёт снизу вверх.

Подробный разбор с деревьями приведён в [grammar.md](grammar.md) и
[diagrams.md](diagrams.md), раздел 10.

### 4.3 Восстановление границ сообщений

Класс `FrameReader` (`common/framing.py`) накапливает поступающие байты во
внутреннем буфере и выделяет из него завершённые сообщения. Незавершённый
остаток сохраняется до следующего чтения.

Важное свойство реализации: **класс работает с байтами и не выполняет
декодирование.** Разрез потока может прийтись на середину многобайтового
символа UTF-8, и попытка декодировать неполный буфер привела бы к ошибке.
Декодирование выполняется только после сборки полного сообщения.

Предельный размер кадра обязателен: без него отправитель, передающий поток
без разделителей, исчерпает память сервера.

### 4.4 Обработка ошибок

Принят принцип: **ошибка в данных клиента не должна разрывать соединение.**

Функция обработки кадра построена так, что не выбрасывает исключений вообще:
любая нештатная ситуация превращается в ответ с кодом ошибки. В противном
случае одна некорректная строка обрывала бы весь сеанс.

Разрыв соединения предусмотрен в двух случаях:

- превышение размера кадра — позиция в потоке потеряна, продолжать нельзя;
- достижение предела одновременных подключений — обслуживание невозможно.

В обоих случаях клиенту отправляется код ошибки, и лишь затем соединение
закрывается.

Исключение, возникшее в обработчике команды, возвращается клиенту как
`INTERNAL_ERROR` с нейтральным текстом, а трассировка записывается в журнал.
Передача внутренних подробностей наружу нежелательна: по тексту исключения
можно восстановить структуру и версии программного обеспечения сервера.

### 4.5 Защита от некорректных и злонамеренных данных

Каждое ограничение закрывает конкретный способ нарушения работы сервера.

| Ограничение | Значение | Предотвращает |
|---|---|---|
| Длина кадра | 4096 байт | Поток без разделителей, исчерпывающий память |
| Длина выражения | 1000 символов | Чрезмерное время разбора |
| Длина записи числа | 100 символов | Арифметику с целыми в тысячи разрядов |
| Глубина вложенности | 50 уровней | Переполнение стека рекурсивного анализатора |
| Величина результата | 10³⁰⁸ | Длительные вычисления с большими числами |
| Таймаут бездействия | 300 секунд | Удержание потока молчащим клиентом |
| Одновременных подключений | 64 | Исчерпание памяти потоками |
| Объём вычитывания при разрыве | 64 КБ | Удержание потока при закрытии соединения |

Наименее очевидное — ограничение глубины вложенности. Анализатор рекурсивного
спуска на каждой открывающей скобке уходит на уровень рекурсии глубже. Строка
из тысячи скобок вызвала бы переполнение стека, причём отказ выглядел бы
необъяснимо: его причина лежит не в логике программы, а в среде выполнения.

### 4.6 Кроссплатформенные особенности

При реализации учтены два расхождения между Windows и POSIX-системами.

**Повторное использование адреса.** После остановки сервера соединения
остаются в состоянии `TIME_WAIT`, что может помешать повторному запуску.
В POSIX-системах для этого предназначен параметр сокета `SO_REUSEADDR`.
В Windows он имеет иной смысл: позволяет постороннему процессу привязаться
к уже занятому порту и перехватывать подключения. Правильный параметр для
Windows — `SO_EXCLUSIVEADDRUSE`. Выбор выполняется по платформе.

**Кодировка стандартного вывода.** При перенаправлении вывода в файл или канал
Python в Windows использует системную кодировку, а не UTF-8, что искажает
кириллицу в журналах. Поток вывода принудительно переключается на UTF-8.

## 5. Тестирование

### 5.1 Организация

Тестирование выполняется на двух уровнях:

- **модульное** — проверка отдельных компонентов без сети;
- **интеграционное** — проверка системы целиком через реальные сокеты.

Запуск: `python -m unittest discover`

### 5.3 Ключевые проверяемые свойства

1. Результат разбора **не зависит от того, как поток байт поделён между
   чтениями** — проверяется побайтовой подачей и разрезом внутри
   многобайтового символа.
2. Приоритет операций соблюдается без явного задания.
3. Ошибка в данных клиента не разрывает соединение.
4. История вычислений изолирована между соединениями.
5. Несколько клиентов обслуживаются одновременно.
6. Код Python, переданный вместо выражения, не выполняется.

### 5.4 Дефекты, выявленные при разработке

Четыре дефекта обнаружены запуском системы, а не чтением кода.

| № | Дефект | Причина | Исправление |
|---|---|---|---|
| 1 | Журнал с кириллицей приводил к ошибке декодирования у получателя | Python в Windows пишет в канал в системной кодировке | Принудительное переключение вывода на UTF-8 |
| 2 | Штатный обрыв связи клиентом записывался с уровнем `ERROR` | Перехватывался только `ConnectionResetError`, Windows возвращает `ConnectionAbortedError` | Перехват общего предка `ConnectionError` |
| 3 | Уведомление о превышении размера кадра не доходило до клиента | Закрытие сокета с непрочитанными входящими данными вызывает аварийный сброс соединения | Корректное закрытие с ограниченным вычитыванием остатка |
| 4 | Тесты ожидали код `UNKNOWN_CHAR` для выражения `2 ** 3` | Символ `*` допустим лексически, ошибка является синтаксической | Исправлены тесты, различие описано в документации |

Дефект №3 представляет отдельный интерес: он показывает, что закрытие сокета
не гарантирует доставку ранее отправленных данных.

## 6. Результаты

### 6.1 Реализованная функциональность

- Сервер, принимающий подключения по TCP и обслуживающий до 64 клиентов
  одновременно.
- Прикладной протокол поверх TCP с восстановлением границ сообщений,
  четырьмя командами и двенадцатью кодами ошибок.
- Собственный синтаксический анализатор арифметических выражений: четыре
  операции, скобки произвольной вложенности, унарные знаки, целые и дробные
  числа.
- История вычислений в пределах соединения.
- Консольный клиент с указанием позиции ошибки в выражении.
- Настройка через аргументы командной строки и переменные окружения.
- Журналирование с уровнями и указанием потока.
- 129 автоматических тестов.

### 6.3 Ограничения текущей версии

- История не сохраняется между подключениями.
- Модель «поток на клиента» ограничивает масштабирование сотнями соединений.

## 7. Заключение

Поставленная задача выполнена. Разработана клиент-серверная система, в которой
самостоятельно реализованы транспортный уровень на сокетах, прикладной протокол
с восстановлением границ сообщений и синтаксический анализ выражений.

Основные результаты, имеющие значение за пределами конкретной задачи:

1. **Опыт работы с потоковым транспортом.** Свойство TCP не сохранять границы
   сообщений проверено экспериментально, а не принято на веру, и на нём
   построено проектное решение.
2. **Понимание границы доверия к внешним данным.** Отказ от `eval()` и система
   ограничений исходят из того, что данные из сети поступают от произвольного
   отправителя.
3. **Проектирование конкурентности через минимизацию общего состояния.**
   Условия для состязаний устранены, а не закрыты блокировками.

Возможные направления развития:

- переход на асинхронный ввод-вывод для масштабирования;
- расширение языка выражений: возведение в степень, функции, переменные;
- шифрование канала средствами TLS;
- сохранение истории и аутентификация пользователей.
