# Протокол обмена

Версия: **1.0**

Документ описывает договорённость между клиентом и сервером. Он написан до кода
намеренно: если протокол не зафиксирован заранее, клиент и сервер неизбежно
разъедутся в мелочах.

---

## 1. Транспортный уровень

| Параметр | Значение |
|---|---|
| Протокол | TCP |
| Семейство адресов | IPv4 (`AF_INET`) |
| Тип сокета | `SOCK_STREAM` |
| Адрес по умолчанию | `127.0.0.1` |
| Порт по умолчанию | `9000` |
| Кодировка | UTF-8 |
| Инициатор соединения | Клиент |
| Модель обмена | Запрос — ответ, строго по очереди |

Соединение живёт до тех пор, пока клиент не отправит команду `quit` или не
закроет сокет. Один клиент может отправить сколько угодно запросов подряд —
переподключаться на каждое вычисление не нужно.

Сервер **никогда не отправляет ничего по своей инициативе**. На каждый запрос
приходит ровно один ответ. Это упрощает клиента: ему не нужен отдельный поток
на приём.

## 2. Границы сообщений (фрейминг)

Это центральная часть протокола, и её нужно понимать точно.

**TCP не сохраняет границы сообщений.** Он гарантирует только, что байты дойдут
все, в правильном порядке и без искажений. Два вызова `send()` на стороне
клиента могут прийти в один `recv()` на стороне сервера — или наоборот,
разрезаться на произвольные куски:

```
Клиент отправил двумя вызовами:   {"cmd":"ping"}     {"cmd":"calc",...}

Сервер может получить:
  {"cmd":"ping"}{"cmd":"calc",...}         склеилось
  {"cmd":"ping"}      {"cmd":"calc",...}   совпало
  {"cmd":"pin       g"}{"cmd":"ca          разрезало посередине
```

Поэтому границы задаются явно.

### Правило

**Одно сообщение — одна строка, завершённая символом перевода строки (0x0A).**

- Символ возврата каретки (0x0D) непосредственно перед переводом строки
  игнорируется. Это нужно, чтобы сервер можно было проверять telnet-клиентом
  с Windows, который шлёт оба символа.
- Внутри тела сообщения перевод строки встречаться не может: JSON сериализуется
  в одну строку, а переводы строк внутри значений экранируются средствами
  самого JSON.
- Приём выполняется с накоплением в буфер: читать из сокета, дописывать в буфер,
  выделять из него завершённые строки, остаток сохранять до следующего чтения.

### Ограничение размера

Максимальная длина одного кадра — **4096 байт**, включая завершающий перевод
строки.

Ограничение обязательно. Без него клиент, отправляющий бесконечный поток без
переводов строки, заполнит память сервера — отказ в обслуживании одной строкой.

При превышении сервер отвечает ошибкой `FRAME_TOO_LONG` и **закрывает
соединение**: продолжать нельзя, потому что позиция в потоке потеряна и
непонятно, где начинается следующее сообщение.

### Признак разрыва

Чтение, вернувшее ноль байт, означает, что противоположная сторона закрыла
соединение. Это единственный корректный признак разрыва — исключение по таймауту
разрывом не является.

### Альтернатива: префикс длины

Промышленный вариант — передавать сначала 4 байта с длиной тела, затем ровно
столько байт. Он работает с любыми данными, включая бинарные, и не требует
экранирования.

Здесь выбран разделитель, потому что данные текстовые, а протокол хочется
набирать руками при отладке. Для передачи файлов или изображений выбор был бы
обратным.

## 3. Формат сообщений

Тело кадра — **JSON-объект**. Не массив, не скалярное значение.

### Запрос

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `cmd` | строка | да | Имя команды |
| `id` | строка или число | нет | Идентификатор запроса; если задан, возвращается в ответе без изменений |
| остальные | — | зависит от команды | Аргументы команды |

Поле `id` в текущей схеме «запрос — ответ» не обязательно: ответы приходят
строго по порядку. Оно заложено на будущее — если протокол когда-нибудь станет
асинхронным, сопоставлять ответы с запросами будет нечем.

### Ответ

| Поле | Тип | Когда присутствует | Описание |
|---|---|---|---|
| `status` | `"ok"` или `"error"` | всегда | Результат обработки |
| `id` | строка или число | если был в запросе | Копия `id` запроса |
| `result` | зависит от команды | при `status: "ok"` | Полезная нагрузка |
| `code` | строка | при `status: "error"` | Машиночитаемый код ошибки |
| `message` | строка | при `status: "error"` | Пояснение для человека |
| `position` | число | при синтаксических ошибках | Индекс символа в выражении, где обнаружена ошибка (с нуля) |

**Поле `status` есть всегда.** Клиент сначала смотрит на него и только потом
трогает остальное. Логика вида «если пришло `result`, значит успех» — ошибка:
она развалится при первом же расширении протокола.

**Код ошибки отделён от текста.** Программа принимает решения по `code`, человек
читает `message`. Разбирать русскую строку в клиенте нельзя — текст может
измениться в любой момент.

## 4. Команды

### 4.1 `calc` — вычислить выражение

Основная команда.

| Аргумент | Тип | Обязательный | Описание |
|---|---|---|---|
| `expr` | строка | да | Арифметическое выражение |

Ограничение длины выражения — **1000 символов**. Синтаксис описан
в [grammar.md](grammar.md).

```json
→ {"cmd": "calc", "expr": "2 + 3 * (4 - 1)"}
← {"status": "ok", "result": 11}
```

```json
→ {"cmd": "calc", "expr": "10 / 0"}
← {"status": "error", "code": "DIV_BY_ZERO", "message": "Деление на ноль"}
```

```json
→ {"cmd": "calc", "expr": "2 + * 3"}
← {"status": "error", "code": "SYNTAX_ERROR", "message": "Неожиданный оператор", "position": 4}
```

**О типе результата.** Целочисленный результат возвращается целым числом,
дробный — числом с плавающей точкой. То есть `4 / 2` даёт `2`, а `5 / 2` даёт
`2.5`. Это удобно человеку, но означает, что клиент не должен рассчитывать на
фиксированный тип.

### 4.2 `ping` — проверка живости

Аргументов нет. Нужна для проверки соединения и как простейший тест протокола
до того, как заработает калькулятор.

```json
→ {"cmd": "ping"}
← {"status": "ok", "result": "pong"}
```

### 4.3 `history` — история вычислений

Возвращает последние успешные вычисления **в текущем соединении**. История
живёт в памяти обслуживающего потока и исчезает при отключении.

| Аргумент | Тип | Обязательный | По умолчанию | Описание |
|---|---|---|---|---|
| `limit` | число | нет | 10 | Сколько записей вернуть, от 1 до 50 |

```json
→ {"cmd": "history", "limit": 2}
← {"status": "ok", "result": [{"expr": "2+2", "result": 4}, {"expr": "10/4", "result": 2.5}]}
```

### 4.4 `quit` — завершение сеанса

Сервер отвечает и корректно закрывает соединение со своей стороны.

```json
→ {"cmd": "quit"}
← {"status": "ok", "result": "bye"}
```

## 5. Коды ошибок

| Код | Причина | Соединение |
|---|---|---|
| `BAD_JSON` | Тело кадра не разбирается как JSON или это не объект | сохраняется |
| `BAD_REQUEST` | Нет поля `cmd`, или поле неверного типа, или аргумент недопустим | сохраняется |
| `UNKNOWN_COMMAND` | Команда неизвестна серверу | сохраняется |
| `EXPR_TOO_LONG` | Выражение длиннее 1000 символов | сохраняется |
| `UNKNOWN_CHAR` | В выражении недопустимый символ | сохраняется |
| `SYNTAX_ERROR` | Выражение не соответствует грамматике | сохраняется |
| `DEPTH_EXCEEDED` | Вложенность скобок больше 50 | сохраняется |
| `DIV_BY_ZERO` | Деление на ноль | сохраняется |
| `NUMBER_TOO_LARGE` | Число или результат выходят за допустимый диапазон | сохраняется |
| `INTERNAL_ERROR` | Непредвиденный сбой на сервере | сохраняется |
| `FRAME_TOO_LONG` | Кадр длиннее 4096 байт | **закрывается** |
| `SERVER_BUSY` | Достигнут предел одновременных подключений | **закрывается** |

Общий принцип: **ошибка в данных клиента не должна разрывать соединение.**
Клиент ошибся в выражении — получил ошибку и работает дальше. Разрыв допустим
в двух случаях:

- `FRAME_TOO_LONG` — протокол нарушен настолько, что синхронизация потока
  потеряна: неизвестно, где заканчивается текущее сообщение;
- `SERVER_BUSY` — обслуживать клиента сервер сейчас не может.

`SERVER_BUSY` приходит сразу после подключения, до всякого запроса. Молчаливый
разрыв в этой ситуации выглядел бы для клиента как поломка сети; внятный код
позволяет понять, что сервер жив, просто занят, и повторить попытку позже.

Ошибка на сервере не должна ронять весь сервер: сбой в одном потоке завершает
одно соединение, остальные клиенты продолжают работать.

## 6. Пример сессии целиком

```
клиент → {"cmd": "ping"}
сервер ← {"status": "ok", "result": "pong"}

клиент → {"cmd": "calc", "expr": "2 + 2"}
сервер ← {"status": "ok", "result": 4}

клиент → {"cmd": "calc", "expr": "-3 * (2 + 4)"}
сервер ← {"status": "ok", "result": -18}

клиент → {"cmd": "calc", "expr": "1 / 0"}
сервер ← {"status": "error", "code": "DIV_BY_ZERO", "message": "Деление на ноль"}

клиент → {"cmd": "history", "limit": 3}
сервер ← {"status": "ok", "result": [{"expr": "2 + 2", "result": 4}]}

клиент → {"cmd": "quit"}
сервер ← {"status": "ok", "result": "bye"}
                       (сервер закрывает соединение)
```

Каждая строка завершается переводом строки, который в примере не показан.

## 7. Заложенные расширения

Реализовывать не обязательно, но протокол под них уже спроектирован —
это стоит упомянуть при защите.

- **Версионирование.** Команда `hello` с полем `version`, чтобы сервер мог
  отказать несовместимому клиенту явной ошибкой, а не непонятным поведением.
- **Аутентификация.** Команда `auth` с токеном; до успешной авторизации
  разрешены только `ping` и `auth`. Место в схеме есть, структура ответа
  не меняется.
- **Переменные.** `let x = 5`, затем `x * 2` — состояние на соединение.
- **Функции.** `sqrt`, `sin`, `abs` — расширение грамматики, протокол не меняется.
- **Асинхронный режим.** Несколько запросов без ожидания ответа, сопоставление
  по полю `id`. Именно ради этого `id` заложен с самого начала.
