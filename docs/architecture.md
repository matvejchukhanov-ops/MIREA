# Архитектура

Документ описывает устройство сервера и клиента: из каких частей они состоят,
как обслуживаются несколько клиентов одновременно и что происходит при сбоях.

---

## 1. Общая схема

```
   ┌──────────────┐                        ┌──────────────────────────────┐
   │  Клиент №1   │───── TCP :9000 ───────▶│           Сервер             │
   └──────────────┘                        │                              │
   ┌──────────────┐                        │  ┌────────────────────────┐  │
   │  Клиент №2   │───── TCP :9000 ───────▶│  │ слушающий сокет        │  │
   └──────────────┘                        │  │ (accept в главном      │  │
   ┌──────────────┐                        │  │  потоке)               │  │
   │  Клиент №3   │───── TCP :9000 ───────▶│  └───────────┬────────────┘  │
   └──────────────┘                        │              │                │
                                           │   ┌──────────┼──────────┐     │
                                           │   ▼          ▼          ▼     │
                                           │ поток 1   поток 2   поток 3   │
                                           │   │          │          │     │
                                           │   └──────────┴──────────┘     │
                                           │              │                │
                                           │              ▼                │
                                           │      вычислительное ядро      │
                                           │     (лексер → парсер → счёт)  │
                                           └──────────────────────────────┘
```

Ключевой момент: **сокетов два вида**. Слушающий — один на весь сервер, он
только принимает подключения и никогда не передаёт данные. И по одному
«разговорному» сокету на каждого подключённого клиента, который создаётся
вызовом `accept()`.

## 2. Слои и направление зависимостей

```
   main.py            запуск, аргументы командной строки
      │
      ▼
   tcp_server.py      слушающий сокет, цикл accept, запуск потоков
      │
      ▼
   connection.py      обслуживание одного клиента: фрейминг, цикл запрос-ответ
      │
      ▼
   protocol.py        сборка и разбор JSON-сообщений, коды ошибок
      │
      ▼
   dispatcher.py      сопоставление имени команды с обработчиком
      │
      ▼
   handlers.py        calc, ping, history, quit
      │
      ▼
   calc/              лексер, парсер, вычислитель
```

Зависимости идут строго сверху вниз. Нижние слои ничего не знают о верхних.

**Пакет `calc/` не знает о сети вообще.** Он принимает строку и возвращает число
или бросает исключение. Из-за этого его можно тестировать без запуска сервера,
без сокетов и без потоков — обычными юнит-тестами.

Это не украшательство. Отладка сетевого кода и отладка парсера — две разные
задачи, и смешивать их в одном месте означает не понимать, где именно
сломалось: в разборе выражения, в разборе JSON или в чтении из сокета.

## 3. Жизненный цикл сервера

1. **Создание сокета** — IPv4, TCP.
2. **Настройка повторного использования адреса** — обязательно. После остановки
   сервера соединения остаются в состоянии `TIME_WAIT` на пару минут, и
   повторный запуск может упасть с ошибкой «адрес уже используется». На отладке
   перезапуск происходит десятки раз в час.

   Флаг зависит от системы, и это тот случай, когда одинаковое имя означает
   разные вещи:

   | Система | Флаг | Что делает |
   |---|---|---|
   | POSIX | `SO_REUSEADDR` | Разрешает занять порт, висящий в `TIME_WAIT`, но не отнимает его у работающего процесса |
   | Windows | `SO_EXCLUSIVEADDRUSE` | Явно запрещает другим процессам занять тот же порт |

   На Windows `SO_REUSEADDR` означает совсем другое: он позволяет чужому
   процессу привязаться к уже занятому порту и перехватывать подключения.
   Ставить его на Windows нельзя, поэтому выбор флага сделан по платформе.
3. **Привязка (`bind`)** к адресу и порту.
4. **Перевод в режим прослушивания (`listen`)** с размером очереди — сколько
   клиентов могут ждать, пока сервер занят предыдущим вызовом `accept()`.
5. **Цикл `accept()`.** Вызов блокирующий: главный поток останавливается и ждёт
   подключения. Как только клиент пришёл, `accept()` возвращает новый сокет
   и адрес клиента.
6. **Запуск потока** на этот сокет. Главный поток немедленно возвращается
   к пункту 5 и ждёт следующего.
7. **Остановка** по сигналу прерывания: закрыть слушающий сокет, дождаться
   завершения потоков или закрыть их сокеты принудительно.

## 4. Жизненный цикл одного соединения

```
   клиент                                    поток обслуживания
     │                                              │
     ├──────── TCP-подключение ────────────────────▶│  создан accept()
     │                                              │
     ├──────── {"cmd":"calc","expr":"2+2"}\n ──────▶│
     │                                              │  чтение в буфер
     │                                              │  выделение кадра по \n
     │                                              │  разбор JSON
     │                                              │  поиск обработчика
     │                                              │  лексер → парсер → счёт
     │◀─────── {"status":"ok","result":4}\n ────────┤
     │                                              │
     ├──────── {"cmd":"quit"}\n ───────────────────▶│
     │◀─────── {"status":"ok","result":"bye"}\n ────┤
     │                                              │
     │◀─────── закрытие сокета ────────────────────┤  поток завершается
```

Внутри потока крутится цикл: прочитать кадр — обработать — ответить. Цикл
прерывается, когда клиент прислал `quit`, закрыл соединение, нарушил протокол
неисправимо или истёк таймаут бездействия.

**Чтение с накоплением.** Каждое чтение из сокета дописывает данные в буфер
соединения. Из буфера выделяются все завершённые строки, остаток сохраняется
до следующего чтения. Именно так решается проблема границ сообщений, описанная
в [protocol.md](protocol.md).

## 5. Модель конкурентности

### Почему нужны потоки

И `accept()`, и чтение из сокета — **блокирующие** вызовы. Если сервер в одном
потоке принял клиента и начал с ним разговаривать, он не вернётся к `accept()`,
пока клиент не отключится. Второй клиент будет висеть в очереди неопределённо
долго.

### Выбранное решение: поток на клиента

Главный поток занимается только приёмом подключений. На каждое создаётся
отдельный поток, который живёт ровно столько, сколько живёт соединение.

Потоки помечаются как фоновые (`daemon`), чтобы аварийная остановка сервера
не подвисала в ожидании клиентов, которые могут молчать сколько угодно.

**Достоинства:** просто, читаемо, честно решает задачу, легко отлаживается.

**Недостатки:** каждый поток занимает память под стек, а переключение между
ними стоит процессорного времени. Тысячи одновременных клиентов так не
обслужить. Для учебной задачи с единицами клиентов это несущественно.

### Что разделяется между потоками

Почти ничего — и это сознательное решение.

| Данные | Где живут | Нужна ли синхронизация |
|---|---|---|
| Буфер чтения | локально в потоке | нет |
| История вычислений | локально в потоке | нет |
| Счётчик подключений | общий | да, блокировка |
| Логгер | общий | нет, `logging` потокобезопасен |

Раз общего изменяемого состояния почти нет, **гонок данных почти неоткуда
взяться**. Единственное исключение — счётчик активных подключений: операция
«прочитать, прибавить, записать» не атомарна, и без блокировки два потока могут
затереть изменения друг друга.

Это стоит подчеркнуть при защите: правильная архитектура не борется с гонками,
а устраняет условия для них — минимизируя общее изменяемое состояние.

### Путь масштабирования

Если бы клиентов были тысячи, вместо потоков применялся бы асинхронный
ввод-вывод: один поток обслуживает все соединения, переключаясь между ними
в моменты ожидания. В Python это `asyncio`, под ним — системные механизмы
`epoll` (Linux) или `IOCP` (Windows).

Смена модели затронула бы только `tcp_server.py` и `connection.py`. Протокол,
диспетчер и вычислительное ядро остались бы без изменений — ради этого
и сделано разделение на слои.

## 6. Обработка ошибок и отказов

Принцип: **отказ должен быть локализован на минимальном уровне.**

| Что произошло | Последствие |
|---|---|
| Ошибка в выражении клиента | Ответ с кодом ошибки, соединение живо |
| Некорректный JSON | Ответ `BAD_JSON`, соединение живо |
| Превышен размер кадра | Ответ `FRAME_TOO_LONG`, соединение закрывается |
| Клиент оборвал связь | Поток корректно завершается, сокет освобождается |
| Таймаут бездействия | Соединение закрывается, поток завершается |
| Непредвиденное исключение в обработчике | Ответ `INTERNAL_ERROR`, запись в лог с трассировкой, соединение живо |
| Непредвиденное исключение в потоке | Завершается один поток, сервер и остальные клиенты работают |

Отдельно про обрыв: клиент может закрыть окно в любой момент, в том числе
посреди отправки. Поток обязан это обработать и освободить сокет. Иначе
после десятка отладочных запусков в системе накапливаются повисшие
соединения и исчерпываются дескрипторы.

## 7. Защита от злоупотреблений

Данные приходят из сети, а значит **им нельзя доверять**. Каждое ограничение
закрывает конкретный способ положить сервер.

| Ограничение | Значение | Что предотвращает |
|---|---|---|
| Длина кадра | 4096 байт | Поток без переводов строки, заполняющий память |
| Длина выражения | 1000 символов | Чрезмерное время разбора |
| Длина записи числа | 100 символов | Арифметику с целыми в тысячи разрядов |
| Глубина вложенности скобок | 50 | Переполнение стека рекурсивного парсера |
| Величина результата | 10³⁰⁸ | Произведения больших целых, занимающие процессор надолго |
| Таймаут бездействия | 300 секунд | Молчащие соединения, занимающие потоки |
| Одновременных подключений | 64 | Исчерпание памяти потоками при открытии соединений пачками |
| Объём вычитывания при разрыве | 64 КБ | Удержание потока клиентом, продолжающим слать данные |

Самое неочевидное — глубина вложенности. Парсер рекурсивного спуска на каждой
открывающей скобке уходит на уровень глубже. Строка из тысячи скобок вызовет
переполнение стека, и без явной проверки это будет выглядеть как
необъяснимое падение потока.

## 8. Клиент

Клиент устроен проще сервера, потому что схема обмена строго последовательная:
отправил запрос — дождался ответа — показал результат. Сервер сам ничего
не присылает, поэтому **отдельный поток на приём не нужен** — в отличие от
чата, где сообщения приходят в произвольный момент.

Состав:

| Модуль | Ответственность |
|---|---|
| `main.py` | Разбор аргументов, запуск |
| `connection.py` | Подключение, фрейминг, отправка и приём |
| `cli.py` | Цикл ввода, вывод результатов и ошибок |

Важно: **фрейминг нужен и на стороне клиента тоже.** Проблема границ сообщений
симметрична — ответ сервера точно так же может прийти по частям. Читать «один
раз и разобрать» нельзя.

Поведение при недоступном сервере: сообщить об этом человеческим текстом
и предложить повторить попытку, а не завершиться трассировкой стека.

## 9. Конфигурация

Хост, порт и лимиты не зашиваются в код. Источники, в порядке приоритета:

1. Аргументы командной строки (`--host`, `--port`)
2. Переменные окружения (`CALC_HOST`, `CALC_PORT`)
3. Значения по умолчанию из `config.py`

Такой порядок стандартен: явное указание при запуске перекрывает окружение,
окружение перекрывает умолчания.

## 10. Логирование

Пишется в стандартный вывод и в файл. Уровни:

| Уровень | Что попадает |
|---|---|
| `INFO` | Запуск и остановка сервера, подключения и отключения клиентов |
| `DEBUG` | Каждый запрос и ответ целиком |
| `WARNING` | Ошибки протокола, превышение лимитов |
| `ERROR` | Непредвиденные исключения с трассировкой |

Без логов отладка сетевого кода превращается в гадание: у сетевой ошибки
нет наглядного проявления, кроме того, что «ничего не работает».
